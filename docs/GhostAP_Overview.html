1. What GhostAP is about

The problem: evil twins

An evil twin is a rogue Wi-Fi access point (AP) that copies the network name (SSID) of a legitimate network, for example a college, café or office network. Phones and laptops connect to whichever access point with a known name looks best, usually the strongest one. Once a victim joins the twin, the attacker can watch or manipulate their traffic, or show a fake login page to steal passwords. An evil twin is cheap to build: a laptop with hostapd, a travel router, or simply a phone hotspot renamed to the victim network's name.

The naive defence, "alert when two access points share a name", does not work. Real networks routinely use many access points with the same name (enterprise Wi-Fi, mesh systems, range extenders), so that rule produces a flood of false alarms. In GhostAP's own evaluation it raised false alarms on 73 % of legitimate access points.

The approach: passive, multi-indicator, explainable

  • Passive. GhostAP only listens to two kinds of 802.11 management frames that every access point broadcasts openly: beacons and probe responses (plus deauthentication/disassociation frames, counted without client addresses). It never transmits, never injects frames, never captures user traffic and never decrypts anything.
  • Learns what normal looks like. For each network name it learns, during a short learning period (2 minutes by default) or from a saved baseline, which access points, vendors, channels, security settings, signal levels, clocks and beacon structures are normal.
  • Many weak signals, not one rule. Eight independent indicators each measure one way a twin usually differs from the real network. They are combined into a 0–100 risk score with weights.
  • Over time, not per frame. Scores are smoothed over 30 seconds, so a single odd frame can never raise an alert.
  • Explainable. Every alert lists each indicator's contribution in points, a plain-language reason, and the innocent explanations an analyst should rule out.
Positioning. GhostAP is a Wireless Intrusion Detection and Airspace Assurance system: it detects suspicious access points and checks that the airspace matches what the owner declared. It is deliberately not a wireless intrusion prevention system: it never attacks or disconnects devices over the air.
Ethics and scope. Use GhostAP only on networks you own or are authorised to monitor. Lab evil twins (phone hotspot, hostapd) run only on your own equipment.

3. How GhostAP works: from radio frames to an explained alert

Step 1: capture

On Linux, a USB Wi-Fi adapter is put into monitor mode (tools/kali_monitor.sh), in which it receives every frame on its channel without joining any network. An adapter hears one channel at a time, so GhostAP hops channels (for example 1, 6, 11 or all 2.4 and 5 GHz channels, 0.25 s each). A twin on another channel than the real AP is therefore still heard. Live capture keeps one capture socket open for the whole run and can record everything it keeps to a pcap file for later replay and labelling. GhostAP also works fully offline by replaying a pcap on any operating system.

Step 2: parse

Each beacon or probe response becomes an observation with: time, network name, BSSID (the AP's MAC address), vendor prefix (OUI), channel, tuned frequency, signal strength (RSSI), security (open, WEP, WPA, WPA2, WPA3, transition modes), the detailed RSN fields (ciphers, key management, protected management frames), beacon interval, the AP's internal clock (TSF), sequence number, and a beacon fingerprint (a hash of how the beacon is built). Damaged frames are rejected, never repaired: a bad checksum, a truncated frame or a malformed element is counted and dropped, because a "repaired" frame could invent a network or make a WPA2 network look open.

Steps 3–5: store, profile, baseline

Observations go into a per-session SQLite database. AP profiles (first/last seen, channels, security, signal statistics) are updated incrementally. The baseline is what each network normally looks like: either learned from the first 2 minutes of the session, or loaded from a saved, signed baseline of protected networks (so a twin that is already on the air at start-up is still caught).

Steps 6–9: indicators, score, smoothing, alert

Every 10 seconds of capture time, every access point is evaluated on its last 10 seconds of frames by eight indicators. Their weighted sum is the raw risk score, which is averaged with the two previous rounds. When the smoothed score reaches 30 an alert is raised (MEDIUM), at 60 it escalates to HIGH. Sections 4 and 5 explain this in detail.

Steps 10–11: dashboard, notifications, evaluation

The web dashboard shows a plain verdict, alerts ranked by risk, every network and AP, a side-by-side comparison of a suspicious AP with the real ones, risk timelines, incidents and evidence. Alerts can be sent to webhooks, phone push, e-mail or a SIEM. The evaluation tools measure accuracy on labelled captures.

4. How GhostAP detects an evil twin: the eight indicators

Each indicator looks at one access point (one SSID + BSSID pair) and returns a value between 0 (nothing suspicious) and 1 (strongly suspicious), plus a reason in plain language. Each targets something a twin finds hard or expensive to copy, and each has known innocent explanations, which the alert lists.

IndicatorWeightWhat it measures and when it firesWhy it works / innocent causes
Security downgrade3.0The AP offers weaker security than the network used in the baseline: WPA2 → WPA = 0.5; → WEP or open = 1.0. A detailed check also catches weaker parts of WPA2/WPA3: a broken TKIP cipher, a missing protected-management-frames requirement, WPA3 → WPA3/WPA2 transition, enterprise → password.Most twins are open or use a different password because the attacker does not know the real one. Innocent: a misconfiguration or a guest network change.
New BSSID / vendor2.0The BSSID was not in the baseline. Same vendor prefix as the real APs = 0.3 (could be a newly added AP); an unknown vendor or a randomised (locally administered) MAC = 1.0.Laptops and phones used as twins have other vendors or random MACs. Innocent: a new AP from another brand, a mesh node.
Channel deviation1.0A new BSSID on a channel the network never used = 1.0; a known BSSID that changed channel = 0.5.Twins often pick their own channel. Low weight: real networks change channel too (automatic channel selection).
Signal (RSSI) jump1.5The AP is much stronger than expected: more than max(6 dB, 3σ) above its own baseline (known BSSID) or the strongest baseline AP (new BSSID), reaching 1.0 at 10 dB beyond that margin. Only frames heard on or next to the AP's own channel are used.Attackers sit close to victims to win the "strongest AP" race. Innocent: the sensor was moved, power increased.
TSF / clock anomaly2.0Every AP has a microsecond counter (TSF) that runs from boot. Fires on a counter reset (reboot, or two devices using one address), on an uptime far below the network's other APs (log-scale ratio: a device booted seconds ago next to APs up for days), or on a change in clock drift of a known address, measured against other APs' clocks.A twin is usually freshly started, and a cloned address on other hardware has a different crystal. Innocent: a reboot or firmware update.
Beacon fingerprint2.5A hash of how the beacon is built: order of information elements, rate sets, HT/VHT/HE capabilities, extended capabilities, vendor element types. A new BSSID whose structure matches none of the network's = 1.0; a known BSSID whose structure changed = 0.6.Router firmware, Linux hostapd and phone hotspots build beacons differently, even when SSID, vendor, channel and security are copied. Innocent: a firmware update, a different AP model.
BSSID conflict (clone)2.5One address seems to be used by two transmitters: frames keep alternating between channels (unless one sequence counter continues across the flips, which means one radio), the same address is heard at two clearly separate signal levels at the same time, or sequence numbers repeatedly go backwards.A twin that clones the real BSSID cannot share its frame counter. Hard to explain innocently.
Beacon interval / rate1.0The advertised beacon interval differs from the network's usual one, or the AP beacons much faster than its own interval allows (a beacon-flood or fake-AP tool).Different software uses different defaults. Innocent: a configuration change.

Σ weights = 15.5. Weights are set in config.yaml; per-network switches can turn single indicators off and change the alert threshold. TSF uses each AP's first frames and full reset history, not just the 10-second window.

5. Scoring, temporal smoothing and alerts

R = ( Σ wi · xi ) / ( Σ wi ) × 100

xi is indicator i's value (0–1) and wi its weight. A twin that only differs in vendor (1.0 × 2.0) scores 12.9; an open twin with a new random MAC, a new structure, another channel and a stronger signal scores 50–60.

  • Every 10 s (capture time) each AP is scored using only its frames from the last 10 s.
  • Smoothing: the shown score is the mean of the last 3 raw scores, counting 0 while the AP is silent. One odd beacon therefore adds at most a third of its score and cannot raise an alert on its own.
  • Levels: LOW < 30 ≤ MEDIUM (alert) < 60 ≤ HIGH.
  • Signatures as score floors: KARMA, look-alike names and known attack tools raise the score to a minimum value instead of adding weight, so they cannot shift the evaluated numbers.
  • Alert content: level, peak score, when it first fired and when it reached HIGH, every indicator's value × weight = points with a reason, and a list of possible benign causes to rule out.
  • Incremental: each round reads only new frames; a test proves incremental scoring equals a one-shot run. Detector memory is capped (30 minutes of history by default) without changing scores.

6. The other detectors and signatures

DetectorWhat it looks for
KARMA / MANA (F001)One radio answering for three or more different network names: rogue-AP tools answer every name a phone asks for.
Look-alike names (F002)A name that imitates a known network: one or two characters different, homoglyphs, case changes (e.g. "MVSR_WIFI" vs "MVSR_WiFi"). The look-alike is then judged against the network it imitates.
Attack-tool fingerprints (F003)Beacon structures / vendor prefixes of known tools from a library file (format and loader built; real fingerprints come from lab recordings).
Deauthentication bursts (F005)Many deauthentication/disassociation frames against one AP within 10 s (10 = MEDIUM, 30 = HIGH), used to push victims onto a twin. Client addresses are never stored; reason codes are, and "station is leaving" frames count one third. The alert names the most common reason and flags login-failure storms.
Beacon flood (F008)Many new radios appearing within a minute (tools such as mdk), after the warm-up.
Duplicate-SSID baselineThe naive comparison detector: flags every AP whose name is used by more than one AP. Shown only "for comparison" so evaluations can prove GhostAP is better.
Incidents (F012)Related alerts (same network, close in time, deauth bursts plus a twin) grouped into one incident with a timeline story.

7. A worked example from a real live test

On 14 November 2026 GhostAP ran live on Kali Linux with the project's adapter. The lab router (WPA2, channel 2) was learned during the 2-minute learning period. Then the owner's phone hotspot was renamed to the router's network name and switched on without a password. GhostAP raised a MEDIUM alert at its first scoring round after the hotspot appeared (about 11 s):

10. Security and privacy by design

Security of the dashboard

  • Everything received over the air (network names, reasons) is HTML-escaped before display.
  • Strict Content Security Policy: no inline scripts, all JavaScript served locally (works offline).
  • Bound to localhost by default, with a Host-header check against DNS rebinding.
  • Every write request must be JSON and same-origin (cross-site request forgery defence); 64 KB request limit.
  • Roles enforced on the server; admin-only endpoints listed centrally.
  • Token login when exposed to the network; optional HTTPS, two-factor sign-in.
  • Signed saved baselines with approval and a full audit log.

Privacy and safety

  • Strictly passive: no transmission, injection, deauthentication or decryption.
  • No client device addresses are stored, not even for deauthentication frames.
  • Captures and databases stay local (never committed to git).
  • Notifications, AI help and sensor reporting are off by default; secrets come only from environment variables.
  • The opt-in AI feature hides network names and addresses from the model.
  • Damaged frames are dropped, never "repaired" into fake evidence.

Three twins from one phone in one location is enough to show GhostAP works on real radio traffic and to find real bugs (four were found and fixed), not enough to estimate its accuracy in general. The configured alert threshold (30) was not tuned on these captures.

Performance (live, measured)

About 15 % of one CPU core and 113 MB of memory at about 32 stored frames per second from about 45 networks; API responses in 1–3 ms; no damaged frames in the last run. A multi-hour soak test is in progress.

12. Limitations and what comes next

Known limitations

  • A twin that copies everything, including the beacon structure, the security and the channel (synthetic scenario s11), is missed: beacons alone cannot separate it from a new legitimate AP.
  • Same-security twins have a thin margin (live scores 31–38 against a threshold of 30).
  • A twin running during the learning period is learned as normal, unless a signed saved baseline is used; the contamination checks now flag the common cases.
  • Hardware: one sensor, 2.4 and 5 GHz only (no 6 GHz), one antenna (no direction finding).
  • Weights are expert judgement, not yet learned from enough real data.
